# Synthesis (round 3)

## Convergence (where architects agree)

- **(realizability, action-model, operability, testability, contrarian): redirect-first / mirror-deferred is over-determined.** All five independently land on shipping XDP-native redirect first and deferring mirror. The forcing fact is a hard kernel constraint, not a preference: `bpf_clone_redirect` is verifier-rejected under `BPF_PROG_TYPE_XDP`, so true clone-and-continue *requires* a second program on a TC/TCX hook — which propagates into a second pin, a second unit failure-domain, a broken one-frame test invariant, and an oracle the deterministic in-process path cannot cover.
- **(realizability, action-model, operability): redirect is lifecycle-cheap and folds into the existing pipeline.** `bpf_redirect_map(&devmap, key, flags)` + `XDP_REDIRECT` adds one userspace-filled pinned map (`DEVMAP`), zero new hooks/qdiscs/units; the devmap is "just another pinned map" the `materialize → maps` step fills, and detach rides the existing bpffs sweep.
- **(action-model, contrarian, realizability): the action ABI was pre-shaped for this and the leanest extension touches only the enum.** Grow `enum xdpmf_action_type` (verified `xdpfilter.h:272-276`, with the in-code "future MVP-3.8+ may extend (MIRROR/RL/TAG)" comment at `:275`); the action axis is deliberately kept RAW through `CompiledRuleset` so no mask-lowering changes. The new datapath branch is *appended after* the existing `ACTION_DROP` test (verified `classifier.h:195`), so PASS/DROP byte-identity is held by construction for non-steering rules.
- **(testability, operability): observability is a cheap slot-extension, not a new pipeline.** A `STAT_REDIRECT`/`STAT_MIRROR` slot (verified `STAT_MAX=4` at `xdpfilter.h:73`; `STAT_PASS_CIDR` is the exact prior widening precedent) flows through the existing `wait_for_stats_sum` harness machinery and the exporter's `verdict_label` switch with near-zero scaffold.
- **(realizability, action-model, contrarian): `BPF_F_BROADCAST` devmap is the *only* XDP-native clone, but its "continue" is a lie for an inline filter.** `XDP_REDIRECT` is terminal; `BPF_F_EXCLUDE_INGRESS` excludes the ingress device from the broadcast set, it does NOT restore the original to the host RX stack. All three explicitly flag it must be rejected as the general mirror primitive (kept only as a topology-specific optimization for a pure-forwarding box).
- **(testability, realizability): redirect is deterministically/in-process provable; mirror is not.** `BPF_F_TEST_XDP_LIVE_FRAMES` (5.18+) executes the redirect side-effect with no veth/netns, but is XDP-only and cannot drive a TC clone — a clean testability argument reinforcing redirect-first.

## Divergence (where architects substantively disagree)

- **(action-model vs contrarian): how much target machinery belongs in slice 1.** Action-model's recommendation prose hedges toward A2 (a `target_id` field in `action_entry`, a new `steering_targets ARRAY[64]`, a `target_resolution` compile pass like `id_to_slot`, and `action_table` changing from identity-keyed to per-rule-allocated). Contrarian prosecutes this as three stacked over-abstractions for a single-destination DPI feed and argues for pure A8 (no target field, no table, no resolution pass, `action_table` stays static + identity-keyed). *Implication:* this is the biggest scope fork — it changes whether slice 1 touches `populate_action_table`'s keying discipline (riskiest brownfield change) or leaves it untouched.
- **(action-model A2 vs action-model A3, both vs contrarian): the slice-2 target representation.** A2 = a verb-generic target table (reused later by tag/RL); A3 = devmap-membership IS the target (strongest validation, lowest redundancy with the redirect mechanism, but no tag/RL reuse and — per testability — nothing offline to assert). Contrarian sides A3 for slice 2 *unless tag/RL are imminent (they are parked)*, and notes both are slice-2+. *Implication:* don't let an out-of-scope tag/RL roadmap drive slice-1 ABI shape.
- **(operability #9 single-unit vs #8 companion-unit): TC mirror lifecycle placement.** Single-unit folds TC attach into the existing `xdpfilter@.service`; companion `xdpfilter-steer@<iface>.service` (BindsTo/After) isolates the mirror failure domain so steering can fail without dropping the critical-path filter. Contrarian rules this *moot for slice 1* (redirect adds zero units) — the fork only exists once mirror lands. *Implication:* defer with mirror.
- **(realizability/action-model "mirror egress copy" vs contrarian "skb-clone on hot RX core"): where mirror's cost lands.** Realizability frames mirror's copy cost as landing "on the mirror egress device, not the RX core"; contrarian corrects that `bpf_clone_redirect` does the skb clone on the RX softirq core, ≫ the 75–198 ns classify cost (`project_perf_envelope`). *Implication:* doesn't change redirect-first, but strengthens the mirror-deferral economic argument and arms the PO fork with a concrete cost.
- **(brief framing vs contrarian): does the product need an in-filter steering datapath at all right now.** The brief calls mirror+redirect "the real product capability"; contrarian surfaces that the canonical `project_dpi_pre_filter_purpose` memory says the DPI handoff is "consumed at the interface/network level" and is "OPEN/DEFERRED" — i.e. mirror may be redundant with a hardware SPAN/tap at the GGSN. The four lenses each dutifully designed the datapath without questioning the premise. *Implication:* mirror's deferral is not just engineering cost — it is a genuine product fork for the PO.
- **(semantics axis — NO architect lens owns it): the steering-verdict interaction policy is unowned.** The brief's "What a good outcome looks like" names *semantics* as one of four axes that may disagree, but no semantics architect exists in the roster. Realizability's `→ Semantics lens` hook (echoed by action-model) raises two real interaction questions it explicitly declines to rule on: (a) when a rule is MIRROR *and* the verdict is DROP, does the original get mirrored before being dropped? (b) can redirect+mirror co-exist on one rule (realizability's datapath *permits* a mirror-tag followed by a redirect verdict, but the *policy* of combining is undefined)? *Implication:* both questions are mirror-gated — they do not block Option 1 (redirect-only) — but they gate the both-verbs path, and because no lens owns them, the interaction policy must be a PO/design input *before any mirror slice is funded*.

## Recommendation (with caveat)

**Lean to Option 1 — Bare Verb.** It is the intersection of all five lenses' leanest selections, it satisfies the brief's hardest invariant (no silent PASS/DROP change) *by construction* rather than by argument, it has zero perf-envelope impact, and it delivers the one steering verb (redirect = inline divert-to-DPI) that is both cheapest to build and least likely to already exist as a network function. Its oracle is the full contrarian three-tier stack — crucially including the **2-iface RX-sink delivery oracle (SELECT-B)** that actually proves the divert lands, not merely the cheap counter+dump tiers. Option 2's per-rule target machinery (A2) and Option 3's mirror (TCX) are a clean forward-compatible superset path — slice 2 adds `target_id` + a target table without redoing the verb/enum/schema work — so deferring them costs no rework. [needs-grep: A8→A2 superset upgrade leaves the enum/schema/materialize untouched]

**Single biggest caveat:** the recommendation assumes the product actually wants an *in-filter* steering datapath now. The canonical `project_dpi_pre_filter_purpose` memory says the DPI handoff is "consumed at the interface/network level" and is "OPEN/DEFERRED" — which most threatens **mirror** (likely redundant with hardware SPAN/tap), and only weakly threatens **redirect** (an inline disposition the classifier already owns). If the PO confirms the network already SPANs/taps for DPI, even redirect's urgency drops; if redirect-to-a-DPI-feed is a genuine inline need, Option 1 is the precise minimal answer. **Secondary caveat (mirror-gated):** the brief's named *semantics* disagreement axis has no architect lens — so the mirror×verdict interaction policy (mirror-then-DROP; redirect+mirror co-existence on one rule) is *unowned* and must be settled as a PO/design input before any mirror slice (Option 3) is funded. This does not touch Option 1.
