# Rule-model classification architecture (Wave B)

> Source lenses: **classifier** (datapath structure), **semantics** (ordering / OR→AND migration),
> **realizability** (eBPF feasibility / portability), **contrarian** (skeptical integrator, read the
> other three). The decision under synthesis: which packet-classification structure realizes
> AND-composed multi-field first-match on the XDP datapath, evolving the existing 5-axis
> `ARRAY_OF_MAPS` + single `active_idx` atomic-swap + `rules_inner→action_table` dispatch — for a
> **narrow Gi-DPI pass/drop pre-selector**, with eBPF as a **model-validation vehicle** (perf deferred)
> and a duty only of **non-foreclosure** to the expansion vision.

## Convergence (where architects agree)

- **(classifier, semantics, realizability, contrarian): OR→AND is a structure change, not a schema bump.** Today each axis is an independent map whose hit carries no knowledge of other axes (`mac_filter.bpf.c:342`/`:393`), so the model is structurally OR; AND-compose is the classic packet-classification problem. realizability's R.8 "extend-as-OR" baseline is scored explicitly as *fails the brief* (cannot AND). This is the load-bearing premise the whole round rests on.
- **(classifier, realizability, contrarian; semantics S.7 corollary): the layered-pipeline / tail-call structure is rejected as the vehicle-stage structure.** realizability is decisive: `PROG_ARRAY` cannot be an `ARRAY_OF_MAPS` inner map, so the program jump-table **cannot ride the single-`active_idx` atomic swap** (R.5) — it fails the brief's own viability filter. classifier scores it the highest-complexity of its three selections and flags it over-engineered at N≤64; contrarian rejects it (stance .7) and confirms the seen-approach was given fair peer treatment, not enforced. **Record it as the Wave-C scale escape hatch, not adopted now.** semantics' tiered model (S.7) only binds to it, so S.7 falls with it.
- **(classifier, realizability): the other two catalog candidates — composite-key (#3) and decision-tree (#4) — are dropped.** Composite-key (classifier.4 / R.3) is a single HASH over a concatenated tuple that works only for all-exact rule subsets and **cannot mix LPM/range/exact primitives in one key** — fatal for the six-primitive target. Decision-tree (classifier.6 / R.6, HiCuts/HyperCuts) is **large-N machinery over-serving a ≤64-rule model-validation vehicle**, at the worst verifier-feasibility + teachability of the field. Neither was selected by any architect; both score-and-drop is unanimous on the parallels that scored them.
- **(classifier, realizability, contrarian): both surviving finalists — sequential-scan and bit-vector — preserve the single-`active_idx` atomic swap and reuse the `rules_outer→rules_inner→action_table` dispatch + `bump_rule` verbatim.** Only the inner-map *value* changes (sequential: `rule_entry`→fat `rule_match`; bit-vector: `allow_entry{present,rule_id}`→`u64` bitmask). The proven race-window benignity (`design.md §5.27`) carries forward untouched for both.
- **(classifier, realizability, contrarian): the current bound `XDPMF_ALLOWLIST_MAX=64` is comfortable for both finalists, and is *exactly* the bit-vector single-`u64` sweet spot.** Both are feasible at N≤64; growth past 64 costs bit-vector a fixed multi-word loop and costs sequential a verify-time re-check.
- **(realizability, contrarian): the portability boundary (Rule IR) makes the structure choice a reversible lowering decision.** realizability's C.4 defines a normalized datapath-agnostic Rule IR (semantics + ordering + default + action-indirection ABOVE the boundary; map types, bitmask widths, atomic-swap, VLAN/IPv6 parse BELOW). Both finalists are lowerings of the same IR, so picking "wrong" is cheap to reverse — contrarian elevates this from a footnote to the decision's safety net.
- **(classifier, realizability, contrarian): IPv6 is non-foreclosed by both finalists — it lands as a parallel `cidr6` LPM_TRIE axis AFTER the AND-architecture.** classifier raised it as a cross-lens hook (`:108` — parallel `cidr6` axis selected by ethertype); realizability ANSWERED it in full (**C.2**, `:141`): a 20-byte LPM_TRIE key `struct xdpmf_cidr_v6{u32 prefixlen; u8 addr[16]}` (prefixlen-first, as `BPF_MAP_TYPE_LPM_TRIE` requires, mirroring `xdpmf_cidr_v4`), a NEW parallel `ARRAY_OF_MAPS` axis (`cidr6_rulesets` + `cidr6_a/_b`, **+3 `kManagedMaps[]` rows**) that **rides `active_idx` for free** and adds a dual L3 parse (`ETH_P_IP` vs `ETH_P_IPV6` after the VLAN skip). Under sequential it is one more inline compare; under bit-vector the v6 trie returns a bitmask exactly like v4 — **zero structural change for either finalist**. contrarian confirms non-foreclosure for both (`:108`). **When: a dedicated slice after the AND-architecture lands (realizability C.2 → catalog §9 step 6, = S3 in the slice sequence below) — "when, not full design"; this round's only duty is not to foreclose it, which is met.**
- **(semantics, contrarian; realizability concurs with a nuance): the ordering fork is resolved at apply-time in the loader, so the datapath stays ordering-agnostic and S.1-vs-S.3 need NOT be resolved this round.** semantics' key finding: most-specific-wins (RFC 8955) is a total order computable at config-load, so it reduces to "sort by specificity rank at apply-time, then run the same first-match datapath" — only the loader's sort key changes. contrarian foregrounds this to free the synthesizer from the fork. (Nuance: realizability notes a bit-vector lowering of most-specific needs the loader to assign bit positions in rank order — apply-time loader bookkeeping, still no datapath comparator.)
- **(semantics, contrarian; classifier endorses the bump): OR→AND migration = M.1 hard cutover via the existing `schema_version` gate (`config.cpp:153`).** v1 stays OR (frozen); AND lives only at v2. contrarian sharpens the detectability mechanism: since dual-mode (M.4) is rejected there is no live OR datapath after the cutover, so the loader **hard-rejects `schema_version:1` files at load** ("re-author to v2") rather than routing them anywhere. ~zero deployed v1 files (project memory: output consumed at the network, no API consumer) ⇒ cost ≈ rewriting the `config_valid_mac_or_cidr.yaml` fixture.

## Divergence (where architects substantively disagree)

- **(classifier vs contrarian) — the crux: bit-vector vs sequential-scan for the vehicle stage.** classifier lands favorably on **bit-vector** ("best brownfield fit", structural elegance, ordering free via `ffsll`, loop-free at N≤64). contrarian argues **sequential-scan primary**: re-tested against the brief, bit-vector's headline win (loop-free *perf*) sits in the explicitly-deferred dimension, while its cost (LPM prefix-closure + range/negation/wildcard aux-mask control-plane) lands in *valued* dimensions — correctness, teachability, bug-surface. realizability is deliberately neutral (R.2 wins verifier/topology/atomic-swap; R.1 wins primitive-flexibility/portability/teachability). **Resolving this picks the first slice's shape and the slice sequence.** contrarian additionally flags that the convergence-toward-bit-vector may be partly *internal* catalog-anchoring (§6.2 pre-labelled bit-vector a "Strong candidate"), not independent agreement — a premise to re-test, not inherit.
- **(classifier vs realizability + contrarian) — a falsifiable factual contradiction: does bit-vector foreclose the 10k–500k feed-object door?** classifier OQ#4 (line 114) asserts "bit-vector forecloses 10k-500k feed-objects (memory wall)". realizability C.3 and contrarian both say this is **wrong**: it conflates rule-**COUNT** (capped at bitmask width) with object/**SET** cardinality — a 500k-prefix set is *one big LPM_TRIE returning one rule's single bit*, not foreclosed. **Synthesis adjudication: carry realizability C.3's framing; classifier OQ#4 is the mis-citation.** Consequence: the feed-object door does NOT discriminate between the two finalists, so it must not tilt the structure choice.
- **(classifier + realizability vs contrarian + brief) — where the §6.4 VLAN parse-fix lands in the slice sequence.** classifier endorses catalog §9 as-is (line 116) and realizability says couple the fix "with the VLAN-axis slice (catalog §9 step 4)" (line 140). contrarian argues the parse fix is a **latent bug that breaks dst-IP (step 1)** on the normal VLAN-segmented Gi link (APN=VLAN): shipping dst-IP without it yields a dst-CIDR axis that silently never fires on tagged traffic — the exact bug src-CIDR has today. The brief's own latent-bug framing (`design-brief.md:32` — *"VLAN support must fix the tagged-frame L3 parse path"*) and the contrarian's APN=VLAN argument both place the parse fix at step 1. Implication: if dst-IP ships at step 1 without the parse fix, the headline #1-gap feature is silently broken on tagged Gi traffic. The parse fix (make tagged IP frames reach L3) must split from the VLAN-*match* axis (which stays at step 4).
- **(realizability + contrarian "spike-first" vs commit-now) — is sequential's verifier verify-TIME a blocking unknown?** All three agree the unrolled 64×(~8-field) scan risks verify-*time* blowup / "too complex" rejection (not the 1M instruction ceiling) — but they differ on whether to measure before committing. realizability makes it open Q#5 ("a `/mint-dev` feasibility spike should measure it before committing R.1 for N>64"); contrarian elevates it to the gate of stance .4 (spike both lowerings, decide on evidence); classifier treats it as a known cost, not a blocker. **Implication: whether the first cycle is an architecture-landing slice or a de-risking spike.**

## Composite directions (cross-lens combinations)

### Option 1 — Stay-course bit-vector (brownfield continuity)
- **Composition**: classifier.2 (parallel bit-vector intersection + .9 hybrid range) + semantics.S.1 (first-match-by-ascending-id, `id`=bit position) + realizability.R.2 (minimal-topology bit-vector; per-axis `wildcard` baseline) + contrarian.3 (bit-vector primary, honestly caveated). Migration semantics.M.1.
- **First slice scope**: reshape each per-axis inner value `allow_entry{present,rule_id}`→`u64 rule_bitmask`; add per-axis `wildcard_mask`; datapath does per-axis lookup, `acc &= (mask | wildcard)`, `rid = ffsll(acc)-1`, reuse the existing dispatch; bump `schema_version` gate to `{1,2}`. The catalog §9 axis-building slices (steps 1-2) reshape into this rather than being discarded.
- **Risk profile**: **medium** — the datapath is verifier-trivial (loop-free at N≤64), but the control-plane carries the real bug surface: **LPM prefix-closure** (each trie entry must store the OR of all rules whose prefix covers it, else overlapping-prefix rules silently mis-match), range-on-dst-port encoding (R.7 range→prefix-LPM or aux range-table on a Tier-1 field), and wildcard/neg/range aux maps that must *also* swap with `active_idx`.
- **User value cycle 1**: AND-composed dst-IP + L4 port matching ships; first-match ordering falls out of `ffsll` for free.
- **Costs**: TTFW ≈ 1 cycle to land AND; control-plane LOC (prefix-closure algorithm, per-apply bitmask recompute) + more `kManagedMaps[]` rows for aux masks; teaching cost of the wildcard/neg-mask concept; cardinality cliff at N>64 (multi-word + bounded loop). Sacrifices: the "dumb loader" simplicity.
- **Preserves**: 5-axis `ARRAY_OF_MAPS` topology byte-for-byte, single-`active_idx` swap, dispatch chain, native LPM/HASH per-axis lookups, the catalog §9 slice continuity.
- **Open Qs for this option**: (1) Where do the wildcard/neg/range aux structures live to swap atomically — parallel `ARRAY[2]` per axis (like `defaults`) or folded into inner values? (2) Range encoding: R.7 prefix-expansion vs aux range-table — which is cleaner under the verifier + loader? (3) Is per-apply prefix-closure recompute acceptable loader complexity for a *teachable* vehicle?

### Option 2 — Minimal vehicle sequential (recommended)
- **Composition**: classifier.1 (sequential per-rule scan) + semantics.S.1 (first-match-by-ascending-id = native loop order) + realizability.R.1 (fat `rule_match` record, single `rules` array, inline primitives) + contrarian.2 (sequential-primary for the vehicle). Migration semantics.M.1; foundation = realizability.C.4 Rule IR committed first; bit-vector (Option 1) pre-committed as the Wave-C perf-lowering + fallback.
- **First slice scope**: fatten the **already-existing** `rules` axis inner value `rule_entry{present,action_id}`→`rule_match{present, action_id, fields_mask, dst_net/mask, src_net/mask, dport_lo/hi, sport_lo/hi, proto, vlan, ethertype, mac[6]}` (~40B); add a `parse_pkt_key` helper **including the §6.4 VLAN parse fix (C.1)**; replace the two per-axis dispatch branches (`:342`,`:393`) with a `#pragma unroll [0,64)` AND-scan loop, first-match-by-index; bump `schema_version` to 2. Fold proto+port into this slice (avoid building throwaway standalone axes).
- **Risk profile**: **medium** — the one genuine unknown is verifier verify-TIME (cold-attach) of the unrolled 64×(~8-field) scan; *checkable* and bounded (5.15-safe via `#pragma unroll`, no `bpf_loop`). All six primitives — incl. range, set, negation — are trivial inline with zero control-plane subtlety.
- **User value cycle 1**: full six-primitive AND matching incl. the core dst-port range/set and negation, the most teachable structure, *and* the §6.4 latent bug closed (dst-IP works on tagged Gi traffic).
- **Costs**: O(N)/packet — but perf is the brief's explicitly-deferred dimension, so the only material cost lands where we're told not to value it. Discards per-axis LPM/HASH as *match* maps (optionally keep a CIDR LPM adjunct for a dst-IP fast path). Verify-time at full field-set is unmeasured.
- **Preserves**: `active_idx` swap, dispatch chain, `bump_rule`, and the already-existing `rules` axis (smallest *conceptual* delta — one struct widened, one loop added); the Rule IR (the in-map table *is* the portable IR).
- **Open Qs for this option**: (1) Max practical N under the verifier with the full field set — validate in-slice (or via the Option 3 spike) before committing N>64. (2) Keep a CIDR LPM adjunct for the dst-IP fast path, or pure scan? (3) Fold proto+port into the AND slice vs build them as catalog steps 1-2 first?

### Option 3 — IR-first, spike-gated (de-risk; decide on evidence)
- **Composition**: realizability.C.4 (commit the Rule IR now) + semantics.S.1 + semantics.M.1 + realizability.C.1 (VLAN parse fix) + contrarian.4 (spike both lowerings, decide on evidence). The structure choice itself is *deferred* one cycle.
- **First slice scope**: commit only the structure-independent layer — `NormalizedRule` Rule IR emitted by `config.cpp` (not maps), first-match-by-id ordering, M.1 migration gate, and the §6.4 VLAN parse fix. Then a `/mint-dev` feasibility spike implements **both** lowerings of a fixed ~20-rule canonical Gi rule-set and measures: (i) sequential verify-TIME / "too complex" at N=64 full-field; (ii) bit-vector loader LOC + reviewer-flag count for prefix-closure; (iii) teachability in band review. Decide from evidence; the loser's lowering becomes the documented escape hatch.
- **Risk profile**: **low** (the contested call is resolved on measurement, not theory; reversibility guaranteed by the shared IR) — at the cost of +1 cycle before AND matching ships.
- **User value cycle 1**: the §6.4 latent bug closed + `config.cpp` emits the portable Rule IR (real product progress) — but AND matching does NOT ship until cycle 2.
- **Costs**: TTFW +1 cycle (the pivotal slice slips by one). Requires discipline to actually decide after the spike, not perpetually defer. Slightly less satisfying than a clean up-front pick.
- **Preserves**: everything — no structure committed yet; both finalists ride the same IR; full non-foreclosure.
- **Open Qs for this option**: (1) Does the team have appetite to spend one cycle to de-risk vs commit-now? (2) Spike exit criteria — what verify-time threshold (cold-attach seconds) flips sequential→bit-vector? (3) Is the spike's teaching value (dual-purpose band-training) worth the slip on its own?

### Option 4 — Extend-as-OR stopgap (dominated baseline / viability floor)
- **Composition**: realizability.R.8 (add dst-IP/proto/port as more parallel OR `ARRAY_OF_MAPS` axes) + contrarian.6 (don't flip to AND yet). No AND-compose.
- **First slice scope**: add dst-IP (and optionally proto/port) as additional independent OR axes alongside today's MAC-HASH + src-CIDR, plus the §6.4 VLAN parse fix; defer the AND pivot.
- **Risk profile**: **low** (proven pattern, literally "add axes") — but it **does not answer the brief**: the model stays OR-compose, the #1 ask (multi-field AND) is unmet.
- **User value cycle 1**: dst-IP matching ships fast as an OR axis (closes the #1 gap *as an independent selector*, not AND-composed).
- **Costs**: re-work later — when AND lands, these OR axes either reshape (bit-vector) or are discarded (sequential), so this is throwaway unless Option 1 is the eventual pick. Fails non-foreclosure of the AND model in spirit (it defers the architecture rather than evolving toward it).
- **Preserves**: today's datapath entirely.
- **Open Qs for this option**: (1) Is there value in shipping dst-IP as an OR selector *before* the AND architecture, given the catalog says AND is the actual demand? (2) Only rational if the AND pivot is being deferred for reasons outside this brief — is it? Included for span; **dominated by Options 1-3** for the brief's stated AND goal.

## Recommendation

> **PO decision (2026-05-28): Option 3 — IR-first, spike-gated.** The recommendation was re-pointed from Option 2 to Option 3 by the PO's performance priority (see "PO decisions" below): **the maximum performance the eBPF technology allows is the target (then it is a question of cost); drop to merely-"optimal" only if max is very hard.** Under that priority the perf-optimal structure (bit-vector, Option 1) is the desired endpoint and sequential (Option 2) is the fallback-if-very-hard — precisely the conditional Option 3 resolves on measured evidence, so Option 2-as-primary is no longer the lead.

**Direction: commit the structure-independent foundation first, then let a measured spike pick the lowering.** Cycle 1 commits only what both lowerings share — the C.4 **Rule IR** emitted by `config.cpp`, first-match-by-`id` ordering (S.1), the **M.1 hard cutover** (`schema_version:2`; v1 hard-rejected at load), and the **§6.4 VLAN parse-path fix** (C.1) — none of which depend on the structure choice. Then a `/mint-dev` feasibility spike implements **both** lowerings of a fixed canonical Gi rule-set and measures the "how hard is bit-vector" question directly: (i) bit-vector loader LOC + reviewer-flag count for LPM prefix-closure / range encoding / aux-mask atomic-swap; (ii) sequential verify-time / "too complex" at N=64 full-field; (iii) teachability in band review. **Decision rule (PO's): take bit-vector (max perf) unless the spike shows it is very hard, in which case fall to sequential (optimal).** The loser's lowering becomes the documented escape hatch behind the same Rule IR (C.4) — making the pick low-regret either way.

**Recommended slice sequence** (Option 3; `design-brief.md:55`):
- **S1 — IR + foundation + parse-fix (no structure committed)**: `config.cpp` emits the C.4 **Rule IR** (`NormalizedRule`), first-match-by-`id` ordering, **M.1** `schema_version:2` hard-cutover, and the **§6.4 VLAN parse-path fix** (C.1). **The §6.4 parse fix lands HERE — split from the VLAN-match axis (S3) — because the parse bug silently breaks dst-IP on a VLAN-segmented Gi link** (PO-ratified, 2026-05-28). Ships real product progress (IR + parse fix); AND matching does not yet.
- **S2 — spike + AND-architecture landing**: implement both lowerings of a canonical rule-set, measure (i)/(ii)/(iii) above, apply the PO decision rule (bit-vector unless very hard → else sequential), then land the chosen AND-scan/intersection over dst-IP/proto/port (`schema_version:2`). The loser becomes the documented escape hatch.
- **S3 — VLAN-match axis**: add `vlan` as a first-class match field (the tagged-frame *parse path* already exists from S1).
- **S4 — IPv6 v6-LPM axis**: parallel `cidr6` LPM_TRIE axis + dual L3 parse (**C.2**); rides `active_idx`, **+3 `kManagedMaps[]` rows**, zero structural change for the chosen structure. "When, not full design" → here. (PO: exact timing pending real Gi v6 traffic reality.)
- **S5 — feed-objects** (only if confirmed near-term): a large IP-set as a set-membership map *referenced by* a rule (**C.3**); orthogonal to the structure choice; refresh/atomicity lifecycle out of scope this round.

## PO decisions (2026-05-28)

Product-owner resolutions to the human-gate open questions:
1. **Performance**: the 40 Gbps line-rate target is **deferred to a different (non-eBPF) filtering approach**. Within the eBPF vehicle, **aim for the maximum performance the technology allows** (then it is a question of cost); **drop to "optimal" only if max is very hard.** → re-points the recommendation to **Option 3** (bit-vector target, sequential fallback, decided by the spike).
2. **Rule count**: **≤64 is enough for now**; growth past 64 is a separate future feature. → single-`u64` bit-vector / bounded sequential both fine; the "N stays ≤64" hidden assumption is retired.
3. **Ordering default** (first-match-by-`id` vs most-specific-wins): **open — to be decided by which fits the use-cases.** Decoupled from the structure (sort-at-load); `S.1` first-match-by-`id` is the safe vehicle default, `S.3` reachable later via the loader sort key.
4. **v1 config compatibility**: **zero deployments; backward-compatibility not required.** → **M.1** hard cutover confirmed safe; the "deployed v1 files" hidden assumption is retired.
5. **§6.4 VLAN parse-fix sequencing**: **accepted — the parse fix lands in S1**, split from the VLAN-match axis, because dst-IP is otherwise born broken on tagged Gi traffic.

**Verify before/at S1 (not a design blocker)** — the one residual unknown (hidden assumption #5): confirm Gi-vantage frames are plain (optionally VLAN-tagged, QinQ ≤ depth-2) IP with **no residual tunneling** ("dst-IP" is never an inner IP). The shared `parse_pkt_key` helper depends on this for every structure equally.

## Hidden assumptions

- **All architects + the brief assume rule COUNT N stays ≤64 (or ≤256) on the narrow Gi path.** If false (the real deployment needs hundreds of *distinct rules*, not large sets behind few rules), both finalists' comfort evaporates: bit-vector needs multi-word + a bounded loop, sequential's verify-time may reject. Nobody validated the actual rule-count target — only the *current* `XDPMF_ALLOWLIST_MAX=64` literal.
- **The whole sequential-primary case assumes perf is *genuinely* deferred for the entire vehicle phase.** If there is an implicit "must not melt a production Gi link even at the vehicle stage" floor, the trade inverts and bit-vector's loop-free datapath becomes mandatory. The brief says deferred; the recommendation rests on it being literally true, not aspirationally true.
- **Everyone assumes ~zero deployed v1 config files (no external/API consumer).** If false, M.1's hard cutover (reject v1 at load) is a silent breaking change for any operator with hand-authored production configs — the migration's "near-zero cost" verdict collapses.
- **The portability boundary (C.4) assumes rule *semantics* (AND-compose, first-match, all six primitives incl. negation) lower cleanly to *any* future backend.** It was validated only against a software re-lowering (AF_XDP/DPDK run the same scan/IR). A future hardware-offload datapath (e.g., switch/NIC TCAM) with limited range/negation support might not lower the "portable" IR cleanly — the IR's portability is untested against a non-software backend.
- **All architects assume §6.4 (VLAN-tagged frames skipping L3) is the *only* parse-path latent bug, that QinQ depth-2 suffices, and that frames on the Gi vantage are plain (optionally VLAN-tagged) IP with no further encapsulation.** On a GGSN/PGW-Gi link this is plausible (GTP-U is typically terminated upstream), but nobody audited whether the operator's "dst-IP" could ever be an *inner* IP under residual tunneling, or whether VLAN stacking exceeds depth 2. If any of these hold, the `parse_pkt_key` helper (shared by every structure, and by both the IPv4 and IPv6 L3 branches) extracts the wrong L3 header and the entire match model targets the wrong bytes — a defect orthogonal to the structure choice but fatal to all of them.
